# 調査のまとめ（2026-10）

## 出発点の問い（2026-10-15）

キットはロゴや素材の調達には便利だが、使うと出来上がりがかっこよくなるわけではない。AI ならもっと良く作れるのに、先にキットを見せたせいで平凡になるケースもありそう。既存のデザインスキルの紹介、アイコンセット、素材の拡充などで、良くする方法はないか。

原本はいずれも AI の深層調査の出力。ベンダーの主張とプレプリントが多い。下の「確度」はそれを踏まえた目安。

## 確度の目安

- **高**: 公式仕様、公式ドキュメント、一次資料で確認できる事実
- **中**: ベンダーの推奨や定性的な前後比較、小規模なプレプリント
- **低**: 調査者の見立て、計数していない比率、出典のない実務慣行

## 知見

### 構造と線引き

**R1. デザインシステムは層で分かれる。** 原則、スタイルとトークン、コンポーネント、パターン、コンテンツ（文章）。調べた 6 システムはすべてこの分け方。このキットにあるのはスタイルの一部と素材だけで、原則、コンテンツ、テンプレートと作例の層がない。
出典: A-1。確度: 高。関係: 構成全体

**R2. マーケティング中心の企業向けの分量の目安。** 原則 5〜10%、ロゴ・色・書体・素材 30〜35%、声とトーン 20%、テンプレートと作例 30〜35%、コンポーネント 0〜5%。
出典: A の推奨 A。確度: 低（ページ数を数えていない見立て）。関係: 構成全体

**R3. 開放するのは見た目の値、固定するのは役割と振る舞いとアクセシビリティ。** IBM Carbon は「トークンの値は変えてよい、名前と役割は変えない」と明文化している。Apple は「ブランドは常にコンテンツに道を譲る」。GOV.UK は「一貫させるが、画一にはしない」を原則にし、「これは拘束衣でもルールブックでもない」と書く。
出典: A-2、A-3。確度: 高。関係: 1、5

**R4. 強さを段階で書く。** GOV.UK は must / should / do not、Material は Do / Caution / Don't。
出典: A-4。確度: 中。関係: 1、5

**R5. 原則は 3〜5 個、行動できる文で書く。** 動詞で始める一文、「X、ただし Y ではない」、判断の問い、強める場面と弱める場面、例 1 組。形容詞だけの原則は参照されなくなる（旧 Polaris の values）。単体で判断に効くのは GOV.UK の動詞句と Atlassian のトレードオフ文。
出典: A-3、A の推奨 C。確度: 中。関係: 2、38

### 画一化と表現

**R6. 表現の量を場面で配分する。** IBM Carbon は productive（業務、控えめ）と expressive（重要な瞬間、鮮やか）を書体とモーションで使い分け、「表現的なモーションは時折の重要な瞬間に取っておく」と書く。
出典: A-6。確度: 高。関係: 3

**R7. Google の M3 Expressive の研究。** 46 件の研究、18,000 人超。表現的なデザインは全年齢で好まれ、主要な要素を最大 4 倍速く見つけられた。一方で、リストの構造やテキストラベルのような慣習を壊すと使いやすさが落ちる。穏やかな版を好む少数派もいる。銀行アプリのような文脈では向かない場合があると認めている。
出典: A-6、https://design.google/library/expressive-material-design-google-research 。確度: 中（Google の自己報告、査読なし）。関係: 3、4

**R8. 「ロゴを隠しても自社のものと分かるか」を品質の問いにする。** IBM の Uniquely Unified の原則にある自問。
出典: A-3。確度: 高。関係: 4

**R9. ガイドなしの AI はすでに定型に収束している。** Inter、白地に紫のグラデーション、同じ形のカード。比べる相手は「自由な創造性」ではなく「統計的な中心」。固有の値を持つキットは中心から引き離す側に働く。ただし中身が定型に近いと、平凡さを固定してしまう。
出典: C-1、C-2、Anthropic と OpenAI のブログ。確度: 中。関係: 4

**R10. 無難になる原因は 4 つ。** 禁止だけの規則集、空いている部分の扱いを指示しないこと、作例 1 枚を正解として渡すこと、規則が多くて長いこと。
出典: C の冒頭と C-3。確度: 中（隣接する証拠からの推論。直接の比較実験はない）。関係: 構成全体

### 書き方

**R11. 禁止は効きにくく、逆に働くことがある。** 特定の定番を禁止すると、モデルは別の定番に移る（Anthropic のブログ。フォントを禁じると Space Grotesk に収束した）。否定の指示のあと、その対象の出力確率が上がる研究もある（プレプリント）。禁止するなら「代わりにこうする」と理由を添える。
出典: C-5、C の Details、https://claude.com/blog/improving-frontend-design-through-skills 。確度: 中。関係: 5、書き方の方針全般

**R12. 細かい値だけでは判断の信号にならない。** Anthropic は、hex 値の指定のような低い高度の指示と、共有前提に頼る曖昧な指示の中間を狙えと書く。先に高い視点の文脈、次に個別の指示。約 400 トークンの指示で出力が改善し、タイポグラフィの指示だけで大きく改善した。
出典: C-7、Anthropic のブログ（2025-11-12、本文で確認済み）。確度: 中（定性的な前後比較）。関係: 2、6、14

**R13. 作例は複数を、役割を限定して渡す。** 1 枚を正解として渡すと固着する（人間の発想の研究からの類推）。複数を「構造や雰囲気の参考」として渡すと豊かさが上がる。作例を外すと色の多様性が 42% 減った例がある（GameUIAgent、プレプリント）。Anthropic の指針は例を 3〜5 個、多様に。
出典: C-3、C-4、C の推奨 3。確度: 中。関係: 41

**R14. 提示順序はサンドイッチ型。** 冒頭に短い方向性と固定項目、中間に素材、末尾（依頼文）に固定項目を 1 行再掲。長い入力の中間にある情報は使われにくい（Lost in the Middle、査読あり）。
出典: C-7、C の Details。確度: 中。関係: 47、SKILL.md の構成

**R15. 規則は少なく明確に。** ただし指示に従える数の上限はモデル世代で急速に上がっている。
出典: C-7。確度: 中。関係: 構成全体

**R16. 「毎回違うデザインに」は実行できない。** モデルは他のセッションの出力を見られない。案の幅が欲しいときは、1 回の依頼で「方向性の違う 3 案を、それぞれの狙いとともに」と頼む。
出典: C の Details、C の推奨 6。確度: 高（前半）、中（後半）。関係: 47

**R17. 作る前の設計と、作った後の自己批評は品質に効く。** Anthropic の frontend-design は、作る前に色・書体・レイアウト・シグネチャー要素 1 つの案を作らせ、それがありがちな既定値でないか点検させる。
出典: C-6。確度: 中。関係: 8

### 素材とテンプレート

**R18. テンプレートと作例ギャラリーは役割が違う。** テンプレートはそのまま使う正解、ギャラリーは幅を示す例。同じ色と書体で見た目の違う完成例を 6〜10 点並べるのが、画一化を防ぐ最も安い手段。
出典: A の推奨 E。確度: 中。関係: 22〜29、41

**R19. スライドは指示文だけだと数枚でずれる。** pptx のマスターを渡す方法が最も確実。アイコンと画像の指定は特に破られやすい。Anthropic の pptx スキルはテンプレートを読み込んで編集できる。
出典: SlideSpeak の記事（ベンダー）、B-2。確度: 中。関係: 9、10、22

**R20. コーポレートサイトのアイコンの実装（2026-10-15 確認）。** 旧版の Material Icons（塗りあり）が 22 ファイル、Material Symbols Outlined（塗りあり、太さ 400）が DX ページで使われている。よく使われているのは close、keyboard_arrow_right / left、trending_up など。
出典: corporate-site リポジトリの実装。確度: 高。関係: 9、10

### 配布経路

**R21. DESIGN.md。** Google Labs の形式。YAML のトークンと、Overview から Do's and Don'ts までの 8 節の散文。2026-10 時点で alpha。lint（参照切れ、コントラスト）と export（Tailwind、DTCG）の CLI がある。読み手はコーディングエージェント。日本語向けのコミュニティ版 awesome-design-md-jp が行間、字間、禁則、和欧混植を扱う。
出典: B-1、https://github.com/google-labs-code/design.md 。確度: 高。関係: 50、6

**R22. Agent Skills。** 必須は name と description。本文は 500 行未満が推奨。詳細は references/、テンプレートは assets/ に置く。
出典: B-2。確度: 高。関係: 構成全体

**R23. Claude の組織スキル（2026-10-15 確認）。** Team と Enterprise では、オーナーが SKILL.md 入りの zip を一度アップロードすると組織全員に配られ、既定で有効になる。各自はオフにできる。
出典: https://support.claude.com/en/articles/13119606-managing-skills-as-an-admin 。確度: 高。関係: 48

**R24. Claude のデザインシステム（2026-10-15 確認）。** 取り込んだデザインシステムに出力を照らして直してから見せる。管理者が標準を 1 つ承認してロックできる。スライドは Claude Slides が入口で、PowerPoint に書き出せる。Claude Code の `/design-sync` でリポジトリから取り込める。
出典: https://claude.com/blog/claude-design-stays-on-brand-for-daily-work 、B-3。確度: 高。関係: 49

**R25. 薄いスキルと正本の URL。** Vercel の web-design-guidelines は、実行のたびに公開 URL から最新の規約を取得し、生成物を検査する。URL で配る今のキットと同じ考え方で、更新が全員に即座に届く。
出典: B-4。確度: 中。関係: 51、配布の方針

**R26. ブランド MCP。** ロゴ、フォント、スライドのレイアウトのように、文字では渡せないものを届ける経路。良い MCP の条件は、最新であること、構造化、承認と版管理、範囲を絞れること、監査できること。
出典: B-6（ベンダーの記事）。確度: 低〜中。関係: 将来の選択肢

**R27. デザイントークンの標準 DTCG は 2025-10 に安定版。** Style Dictionary、Tokens Studio、Figma が対応。
出典: https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/ 。確度: 高。関係: 21

**R28. llms.txt は任意。** 実際にどの AI が読むかは議論が分かれている。
出典: 2026-10-15 のセッションでの調査。確度: 低。関係: なし

### デザインスキル

**R29. 公式のデザイン系スキル（anthropics/skills）。** frontend-design は Web UI。現行版は「ブリーフの言葉が優先、空いた軸は既定値で埋めない、大胆さは 1 か所」。canvas-design は静止画の方向出し向きで、定型物の量産には向かない。pptx はテンプレートの編集ができる。brand-guidelines は自社版の雛形向きだが、日本語フォントの指定がない。
出典: B-2、C-6。確度: 高（中身）、中（向き不向き）。関係: 46

**R30. frontend-design と併用するときは、固定する項目を明示すれば衝突しない。** 現行版は指定がある部分には従う。「ブランドを全面的に優先」と書くと、元の窮屈さが戻る。
出典: C-6。確度: 中。関係: 46
